# prds

**機能ごとの PRD（Product Requirements Document）の置き場所。今の機能要件と振る舞いの正本はここにある。** 1 つの機能について、なぜ要るのか（目的・背景・ゴール）と、今満たすべきこと（振る舞い・要件・受け入れ条件）を、1 つのファイルにまとめて書く。

プロダクト全体の目的・提供価値・成功条件は [product.md](../product.md) にある。PRD は、それを機能の単位で書く。

2026-11-15 まで、この役割は `docs/specs/` が持っていた。同じ名前のファイルをここに移し、目的・背景・ゴールの節を足し、実現方法の説明を [architecture/](../README.md#architecture) に移した。移す前の履歴は `git log --follow` でたどる。

## 書くこと・書かないこと

| 書く | 書かない（書く場所） |
| --- | --- |
| その機能の目的・提供価値・背景・ゴール | プロダクト全体の目的・対象・原則（[product.md](../product.md)） |
| 閲覧者・テンプレートの利用者・外部のシステム（検索エンジン・SNS など）から見た振る舞い | 実現に使う技術・設定・ファイルの置き場所・機能を支える仕組み（[architecture/](../README.md#architecture)） |
| 守るべき要件（判定のルール・データの扱い・公開範囲・プライバシー・セキュリティ） | 技術を選んだ理由・捨てた案・トレードオフ（[design-docs/](../design-docs/README.md)） |
| 外から観測できる契約（`<head>` に出す値など） | 操作の手順（[runbooks/](../README.md#runbooks)） |
| 受け入れ条件（満たしているかの確かめ方） | まだ実装していない変更の案（design doc の「対象の PRD」） |
| 意図を確かめていない今の振る舞い・決まっていないこと（「実装から読み取れる現状・未確認事項」の節） | |

**要件と実現方法を分ける。** 「閲覧者のブラウザが外の書体の配信に接続しない」は要件なので PRD に書き、「Astro の Fonts API でビルドのときに取ってくる」は実現方法なので architecture に書く。セキュリティ・プライバシー・データの扱いの要件は、技術の言葉が混ざっても PRD に書いてよい。

実装の置き場所は「関連資料」の節にリンクだけ書いてよい。どう実装したかの説明は architecture に書く。

## 要件は変えてよい

- **要件は変わるものとして扱う。** 過去の design doc と違う変更を頼まれても、過去の判断は変更を断る理由にならない
- 変えるときは、今の PRD との違い・影響範囲・トレードオフを確かめる。プロダクト全体の目的や提供価値に関わるなら [product.md](../product.md) も読む。design doc を書く変更（基準は [design-docs/README.md](../design-docs/README.md#いつ書くか)）なら、新しい design doc を書いて承認を得てから実装する。静的なページの追加やテキスト・画像の差し替えなら、PRD を直すだけでよい
- **PRD を直すのは、実装と同じ変更の中。** 実装していない「変更後」を先に書かない。書くと、実装済みの要件と区別がつかなくなる
- 安全性や技術的な制約を外してよいという意味ではない。制約とぶつかる変更は、影響・リスク・取りうる案を示して判断を仰ぐ

## わからないことの扱い

- **背景・課題・ゴールは、根拠があるものだけ書く。** 根拠は product.md・design doc・README・コードの注釈・ユーザーの確認。根拠のない目的・課題・測定指標を作らない。書けないものは「未確認事項」に書く
- **コードにあるからといって、意図された要件とは限らない。** 今の振る舞いはわかるが意図がわからないものは、本文に入れず「実装から読み取れる現状」に書く。確かめられたら本文へ移す
- **「実装から読み取れる現状」は観測の記録で、この先の変更を禁じる制約ではない**
- **今無いだけのものを「対象外」に書かない。** 「対象外」に書くのは、意図して外すと決めたもの（根拠のあるもの）だけ。まだ作っていないだけのものは「実装から読み取れる現状」に書く

## ファイル名

```text
<feature>.md
```

機能やドメインの名前を英小文字の kebab-case で付ける（例: `page-metadata.md`）。

- **要件や振る舞いが変わったら、PRD を増やさずに今のファイルを書き直す。** 増えるのは design doc（変更の検討と判断の記録）のほう。1 つの機能に PRD は 1 つで、新しく作る前に一覧を見て、同じ機能のものがあればそれを直す
- **日付は付けない。** 中身を書き直し続けるので、日付は作った日しか表さず、今の要件かどうかの手がかりにならない。いつ・なぜ変わったかは、`git log --follow` と、その変更の design doc の「対象の PRD」でたどる

## 書き方

[`_template.md`](_template.md) をコピーして使う。該当しない節は「なし」と書いて残す。節ごと消さない。考えた上で空だとわかることのほうが役に立つ。
