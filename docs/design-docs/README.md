# design-docs

**機能の追加・仕様の変更・技術の変更を、どう実現するかを検討し、その判断を残す場所。** 複数の作り方を比べて選ぶ設計変更は、コードを書く前に書き、ユーザーの承認を得てから実装に入る。

**design doc は今の仕様の正本ではない。** 書いた時点の判断の記録。今の仕様は [specs/](../specs/README.md)、今の構成と規約は [architecture/](../README.md#architecture) にある。

## specs と何が違うか

specs は今決まっていることだけを書き、**決める過程が残らない。** 後から読んだ人（次の自分、他のメンバー、AI エージェント）は「なぜこの形なのか」を再現できず、同じ議論をもう一度やる。

design doc は過程ごと残す。**やらないことと、検討して捨てた案が本文に入る。** これがあると、

- 実装中にスコープが広がりかけたとき、「やらないこと」に書いてあるかで止められる
- 「やっぱりこっちの作りでは」と思ったとき、すでに捨てた案かどうかと、捨てた理由が「検討した他の案」でわかる
- AI エージェントに実装させるとき、判断の前提ごと渡せる。仕様だけ渡すと、書いていない部分を勝手に埋められる

**ただし、捨てた案や「この先もやらない」は、その時点の判断であって禁止事項ではない。** 前提が変われば選び直してよい。選び直すときは、捨てた理由が今も当てはまるかを確かめ、新しい design doc に書く。

| | specs | design doc |
| --- | --- | --- |
| 書くこと | 今の振る舞い・制約・受け入れ条件 | 背景・設計・捨てた案・トレードオフ・影響範囲 |
| いつ直すか | 実装が変わるたび | 実装に入るまで。実装後は凍結する |
| 内容が食い違ったら | specs が今の仕様 | 当時の記録として読む |

書くのは実装者。**合意を取るための文書であって、報告書ではない。** 完成した機能の説明を後から書くのは design doc ではない（今の振る舞いは specs に書く）。

## いつ書くか

**複数の作り方を比べて選ぶ必要がある変更だけ書く。** Web サイトはページやセクションを足したり差し替えたりすることが多く、そのたびに design doc を書くと制作の速さを損なう。

| 変更 | design doc |
| --- | --- |
| CMS などからデータを取るようにする | 書く |
| 新しいデータの流れを作る（フォームの送信、外部への保存など）・データの持ち方を変える | 書く |
| 認証・アクセス制御を入れる | 書く |
| 外部サービスと連携する | 書く |
| サーバーの処理を足す・配信の構成を変える | 書く |
| ライブラリ・基盤の選定、構成や規約（architecture）を変える | 書く |
| テンプレートから引き継いだ方針（静的出力を基本にする・JS を必要な機能に限る など）を変える | 書く |
| 静的なページ・セクションを足す | 書かない（specs を直す） |
| 通常の UI の変更・テキストや画像の差し替え | 書かない（振る舞いが変わるなら specs を直す） |
| スタイル調整・リファクタリング | 書かない |
| 通常のバグ修正 | 書かない（原因と直し方は PR に書く） |

**迷ったら、比べて捨てる案があるかで決める。** 作り方が 1 つに決まっていて、specs を直せば説明がつくなら書かない。後から「なぜこの形なのか」と聞かれそうな判断を含むなら書く。

design doc を書かない変更でも、振る舞いが変わるなら specs を、構成や規約が変わるなら architecture を、同じ変更の中で直す。

## ファイル名

書き始めた日を prefix にする。凍結する文書なので、日付で並べる。

```text
<YYYYMMDD>_<topic>.md
```

例: `20260826_user-invitation.md`

## 書き方

[`_template.md`](_template.md) をコピーして使う。各節は次の役割で置いてある。

| 節 | 何のためにあるか |
| --- | --- |
| 概要 | ここだけ読んで他の人に説明できる状態にする |
| 背景 | なぜ今これが要るのか。書けないものは、まだ作るときではない |
| ゴール | 達成したかを判定できる形にする |
| やらないこと | 実装中のスコープの広がりを止める |
| 対象の仕様 | どの specs が、どう変わるか。ここに書くのは変更の案で、specs 本体は実装のときに直す |
| 設計 | 画面・URL・置き場所・データ・処理の流れ |
| 検討した他の案 | 捨てた案と、捨てた理由を残す。後から一番効く |
| トレードオフ | 採った案で失うもの・引き受けるリスク |
| 影響範囲 | 壊れうるものを先に挙げる |
| 未決事項 | 決まっていないことを隠さない |

**設計の「置き場所」は [architecture/directory-structure.md](../architecture/directory-structure.md#置き場所の判断フロー) の判断フローで決める。** ここでディレクトリまで決めておくと、実装時に迷わない。

該当しない節は「なし」と書いて中身を消す。**節ごと消さない。** 空でないことより、考えた上で空だとわかることのほうが役に立つ。

## status の進め方

frontmatter の `status` で状態を持つ。

| status | 意味 | 進めてよい人 |
| --- | --- | --- |
| `draft` | 書いている途中。まだ読まなくていい | 書く人（AI エージェントを含む） |
| `review` | 読んでほしい。ここで合意を取る | 書く人（AI エージェントを含む） |
| `approved` | 合意済み。実装に入ってよい | **ユーザーの明示的な承認があったときだけ** |
| `implemented` | 実装が入った。`pr` に実装 PR を書く | 実装した人（AI エージェントを含む） |
| `superseded` | 別の design doc が置き換えた。冒頭に後継へのリンクを足す | 後継の design doc を書いた人 |

- **`review` から `approved` に進める条件は、「未決事項」が空になり、ユーザーが明示的に承認すること。** 未決のまま実装に入ると、その判断はコードを書く人の手元で勝手に決まる
- **AI エージェントは design doc を自分で承認しない。** 自分で書いた design doc を `approved` にせず、`review` で止めてユーザーに承認を求める。返事が承認かどうか判断がつかないときは、承認かを聞き直す

## 実装したら

1. 実装と同じ変更の中で、specs・architecture・runbooks を今の状態に直す。design doc の「対象の仕様」に書いた変更の案は、ここで初めて specs に入れる
2. design doc を `implemented` にし、`pr` に実装 PR を書く

## 実装後は凍結する

**凍結するのは design doc という記録であって、その機能の仕様や実装ではない。**

- `implemented` になった design doc は、その時点の判断の記録として書き換えない。書き換えると「いつ何を決めたか」が消える
- **仕様や実装は、その後も変えてよい。** 過去の design doc と違う変更を頼まれても、それを理由に断らない。今の specs・architecture との違いと影響を確かめ、複数の作り方を比べて選ぶ変更なら新しい design doc を書く
- 方針を置き換えたら、新しい design doc を書き、古いほうを `superseded` にして冒頭に後継へのリンクを足す
- 凍結した design doc に加えてよいのは、`superseded` への変更と後継へのリンク、`pr` の追記、リンク切れの修正、明らかな誤字の修正だけ

2026-11-15 に一度だけ、ドキュメント体系の移行のために既存の design doc を組み直した（[20261115_docs-system.md](20261115_docs-system.md)）。仕様・規約・手順を specs・architecture・runbooks に移しただけで、判断と理由は書き換えていない。
