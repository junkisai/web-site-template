# design-docs

**機能の追加・要件の変更・技術の変更を、どう実現するかを検討し、その判断を残す場所。** [いつ書くか](#いつ書くか)に当たる変更は、コードを書く前に書き、ユーザーの承認を得てから実装に入る。

**design doc は今の要件や構成の正本ではない。** 書いた時点の判断の記録。プロダクト全体の目的は [product.md](../product.md)、今の機能の要件と振る舞いは [prds/](../prds/README.md)、今の構成と規約は [architecture/](../README.md#architecture) にある。

## PRD・architecture と何が違うか

PRD と architecture は今決まっていることだけを書き、**決める過程が残らない。** 後から読んだ人（次の自分、他のメンバー、AI エージェント）は「なぜこの形なのか」を再現できず、同じ議論をもう一度やる。

design doc は過程ごと残す。**やらないことと、検討して捨てた案が本文に入る。** これがあると、

- 実装中にスコープが広がりかけたとき、「やらないこと」に書いてあるかで止められる
- 「やっぱりこっちの作りでは」と思ったとき、すでに捨てた案かどうかと、捨てた理由が「検討した他の案」でわかる
- AI エージェントに実装させるとき、判断の前提ごと渡せる。要件だけ渡すと、書いていない部分を勝手に埋められる

**ただし、捨てた案や「この先もやらない」は、その時点の判断であって禁止事項ではない。** 前提が変われば選び直してよい。選び直すときは、捨てた理由が今も当てはまるかを確かめ、新しい design doc に書く。

| | PRD | architecture | design doc |
| --- | --- | --- | --- |
| 書くこと | 機能の目的・背景・ゴール・今の振る舞い・要件・受け入れ条件 | 今の技術構成・機能を支える仕組み・規約・技術上の制約 | 背景・変更前と変更後の要件・実現方法・捨てた案・トレードオフ・影響範囲 |
| 時間 | 今の Why と What | 今の How | 当時の How と、それを選んだ理由 |
| いつ直すか | 要件や振る舞いが変わるたび | 構成や規約が変わるたび | 実装に入るまで。実装後は凍結する |
| 内容が食い違ったら | PRD が今の要件 | architecture が今の構成 | 当時の記録として読む |

書くのは実装者。**合意を取るための文書であって、報告書ではない。** 完成した機能の説明を後から書くのは design doc ではない（今の振る舞いは PRD に、今の構成は architecture に書く）。**今の技術構成を記録するためだけに design doc を書かない。**

## いつ書くか

**複数の作り方を比べて選ぶ必要がある変更と、システムの構成・セキュリティ・データの扱いに大きく影響する変更で書く。** 作り方が 1 つしかなくても、重要な変更は設計の記録を残す。一方で Web サイトはページやセクションを足したり差し替えたりすることが多く、そのたびに design doc を書くと制作の速さを損なうので、それには書かない。

| 変更 | design doc |
| --- | --- |
| CMS などからデータを取るようにする | 書く |
| 新しいデータの流れを作る（フォームの送信、外部への保存など）・データの持ち方を変える（DB やデータのスキーマの変更を含む） | 書く |
| 認証・アクセス制御を入れる・権限や公開範囲を変える | 書く |
| 外部サービスと連携する | 書く |
| サーバーの処理を足す・配信の構成を変える | 書く |
| ライブラリ・基盤の選定、構成や規約（architecture）を変える | 書く |
| テンプレートから引き継いだ方針（静的出力を基本にする・JS を必要な機能に限る など）を変える | 書く |
| 複数の機能（PRD）にまたがる重要な変更 | 書く |
| 上のどれにも当たらないが、システムの構成・セキュリティ・データの扱い（整合性を含む）に大きく影響する | 書く |
| 静的なページ・セクションを足す | 書かない（PRD を直す） |
| 通常の UI の変更・テキストや画像の差し替え | 書かない（振る舞いが変わるなら PRD を直す） |
| スタイル調整・リファクタリング | 書かない |
| 通常のバグ修正 | 書かない（原因と直し方は PR に書く） |
| 今の技術構成を記録したいだけ | 書かない（architecture を直す） |

**迷ったら、比べて捨てる案があるか、構成・セキュリティ・データの扱いに影響するかで決める。** どちらにも当たらず、PRD を直せば説明がつくなら書かない。後から「なぜこの形なのか」と聞かれそうな判断を含むなら書く。

design doc を書かない変更でも、振る舞いや要件が変わるなら PRD を、構成や規約が変わるなら architecture を、同じ変更の中で直す。

## ファイル名

書き始めた日を prefix にする。凍結する文書なので、日付で並べる。

```text
<YYYYMMDD>_<topic>.md
```

例: `20260826_user-invitation.md`

## 書き方

[`_template.md`](_template.md) をコピーして使う。各節は次の役割で置いてある。

| 節 | 何のためにあるか |
| --- | --- |
| 概要 | ここだけ読んで他の人に説明できる状態にする |
| 背景 | なぜ今これが要るのか。書けないものは、まだ作るときではない |
| ゴール | 達成したかを判定できる形にする |
| やらないこと | 実装中のスコープの広がりを止める |
| 対象の PRD | どの PRD の要件が、今（変更前）からどう変わるか（変更後の要件案）。プロダクト全体の目的に関わるなら product.md との関係も。ここに書くのは変更の案で、PRD 本体は実装のときに直す |
| 設計 | 実現方法。画面・URL・置き場所・データ・処理の流れ |
| 検討した他の案 | 捨てた案と、捨てた理由を残す。後から一番効く |
| トレードオフ | 採った案で失うもの・引き受けるリスク |
| 影響範囲 | 壊れうるものを先に挙げる |
| 実装後に直す文書 | 実装と同じ変更の中で今の状態に直す PRD・architecture・runbooks・product.md |
| 未決事項 | 決まっていないことを隠さない |

**設計の「置き場所」は [architecture/directory-structure.md](../architecture/directory-structure.md#置き場所の判断フロー) の判断フローで決める。** ここでディレクトリまで決めておくと、実装時に迷わない。

該当しない節は「なし」と書いて中身を消す。**節ごと消さない。** 空でないことより、考えた上で空だとわかることのほうが役に立つ。

`docs/specs/` を `docs/prds/` に移す前（2026-11-15 まで）に書いた design doc では、「対象の PRD」の節は「対象の仕様」という名前で、`docs/specs/` を指していた。

## status の進め方

frontmatter の `status` で状態を持つ。

| status | 意味 | 進めてよい人 |
| --- | --- | --- |
| `draft` | 書いている途中。まだ読まなくていい | 書く人（AI エージェントを含む） |
| `review` | 読んでほしい。ここで合意を取る | 書く人（AI エージェントを含む） |
| `approved` | 合意済み。実装に入ってよい | **ユーザーの明示的な承認があったときだけ** |
| `implemented` | 実装が入った。`pr` に実装 PR を書く | 実装した人（AI エージェントを含む） |
| `superseded` | 別の design doc が置き換えた。冒頭に後継へのリンクを足す | 後継の design doc を書いた人 |

- **`review` から `approved` に進める条件は、「未決事項」が空になり、ユーザーが明示的に承認すること。** 未決のまま実装に入ると、その判断はコードを書く人の手元で勝手に決まる
- **AI エージェントは design doc を自分で承認しない。** 自分で書いた design doc を `approved` にせず、`review` で止めてユーザーに承認を求める。返事が承認かどうか判断がつかないときは、承認かを聞き直す

## 実装したら

1. 実装と同じ変更の中で、文書を今の状態に直す
   - 「対象の PRD」に書いた変更後の要件案は、ここで初めて PRD に入れる
   - 「設計」に書いた実現方法のうち、今の構成になったものは architecture に書く。design doc にだけ残さない
   - 手順が変わったら runbooks、プロダクト全体の目的・提供価値・成功条件が変わったら product.md を直す
2. design doc を `implemented` にし、`pr` に実装 PR を書く

## 実装後は凍結する

**凍結するのは design doc という記録であって、その機能の要件や実装ではない。**

- `implemented` になった design doc は、その時点の判断の記録として書き換えない。書き換えると「いつ何を決めたか」が消える
- **要件や実装は、その後も変えてよい。** 過去の design doc と違う変更を頼まれても、それを理由に断らない。今の PRD・architecture との違いと影響を確かめ、[いつ書くか](#いつ書くか)に当たる変更なら新しい design doc を書く
- 方針を置き換えたら、新しい design doc を書き、古いほうを `superseded` にして冒頭に後継へのリンクを足す
- 凍結した design doc に加えてよいのは、`superseded` への変更と後継へのリンク、`pr` の追記、リンク切れの修正、明らかな誤字の修正、ドキュメント体系の移行に伴うリンクの張り替えと日付付きの移行の注記だけ。本文の意味は変えない

2026-11-15 に一度、ドキュメント体系の移行のために既存の design doc を組み直した（[20261115_docs-system.md](20261115_docs-system.md)）。仕様・規約・手順を specs・architecture・runbooks に移しただけで、判断と理由は書き換えていない。

同じ 2026-11-15 に、`docs/specs/` を `docs/prds/` に移した。既存の design doc にある specs へのリンクは移した先の PRD に張り替え、冒頭に日付付きの注記を足した。本文の「specs」「対象の仕様」は当時の名前のまま残している。
