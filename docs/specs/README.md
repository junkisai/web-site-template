# specs

**今の仕様の正本。** サイトが何を満たすべきか（振る舞い・制約・受け入れ条件）を、機能ごとに 1 ファイルで書く。

## 書くこと・書かないこと

| 書く | 書かない（書く場所） |
| --- | --- |
| 今有効な振る舞いと制約 | 実装の方法・技術選定の経緯（[design-docs/](../design-docs/README.md)） |
| 受け入れ条件（満たしているかの確かめ方） | 構成・置き場所・書き方の規約（[architecture/](../README.md#architecture)） |
| 意図が確かめられない振る舞い（「未確認事項」の節に） | 操作の手順（[runbooks/](../README.md#runbooks)） |
| | まだ実装していない変更の案（design doc の「対象の仕様」） |

実装の置き場所（どのファイルにあるか）は「関連」の節にリンクだけ書いてよい。どう実装したかの説明は書かない。

## 仕様は変えてよい

- **仕様は変わるものとして扱う。** 過去の design doc と違う仕様の変更を頼まれても、過去の判断は変更を断る理由にならない
- 変えるときは、今の specs との違い・影響範囲・トレードオフを確かめる。design doc を書く変更（基準は [design-docs/README.md](../design-docs/README.md#いつ書くか)）なら、新しい design doc を書いて承認を得てから実装する。静的なページの追加やテキスト・画像の差し替えなら、specs を直すだけでよい
- **specs を直すのは、実装と同じ変更の中。** 実装していない「変更後」を先に書かない。書くと、実装済みの仕様と区別がつかなくなる
- 安全性や技術的な制約を外してよいという意味ではない。制約とぶつかる変更は、影響・リスク・取りうる案を示して判断を仰ぐ

## わからないことの扱い

**コードにあるからといって、意図された仕様とは限らない。** 本文に書くのは、意図を確かめられたもの（design doc・README・コードの注釈・ユーザーの確認）だけにする。今の振る舞いはわかるが意図がわからないものは、本文に入れずに「未確認事項」に書く。確かめられたら本文へ移す。

## ファイル名

```text
<feature>.md
```

機能やドメインの名前を英小文字の kebab-case で付ける（例: `page-metadata.md`）。

- **仕様が変わったら、spec を増やさずに今のファイルを書き直す。** 増えるのは design doc（変更の検討と判断の記録）のほう。1 つの機能に spec は 1 つで、新しく作る前に一覧を見て、同じ機能のものがあればそれを直す
- **日付は付けない。** 中身を書き直し続けるので、日付は作った日しか表さず、今の仕様かどうかの手がかりにならない。いつ・なぜ変わったかは、`git log --follow` と、その変更の design doc の「対象の仕様」でたどる

## 書き方

[`_template.md`](_template.md) をコピーして使う。該当しない節は「なし」と書いて残す。
